# Tailbase Blocks

Gutenberg blocks for the Tailbase theme. The plugin has **its own Tailwind CSS v4 build** and works with any theme.
(It replaces the former `tt-theme-blocks` plugin. The old blocks were removed; their code is still in the git history.)

## Quick start

```bash
npm install
npm run build      # production build into build/
npm start          # watch mode
npm run lint:js    # lint
```

Then activate **Tailbase Blocks** in Plugins. The blocks appear in the **Tailbase** category of the inserter.
`build/` is not committed, so run `npm run build` after cloning or deploying.

## Structure

```
tailbase-blocks.php           registers every build/<block>/block.json + the "Tailbase" block category
src/
  styles/tailwind.css         shared Tailwind setup (prefixed, no reset, no layers)
  styles/tokens.css           design tokens (colors) that read the theme's palette
  <block>/
    block.json
    index.js                  registerBlockType + imports style.css
    edit.js / save.js         editor UI / saved markup
    classes.js                every Tailwind class of the block (complete strings)
    style.css                 imports the shared setup and scans only this block's folder
    controls/                 block controls: one file per control, rendered in controls/index.js
build/<block>/                webpack output (git-ignored)
```

## How the styling avoids conflicts

- **Prefix `tbb:`**: all classes are written as `tbb:flex tbb:p-8`, and theme variables are `--tbb-*`. They cannot
  collide with the theme's Tailwind classes.
- **No reset (preflight)**: the plugin never restyles the theme's elements. Set margins, sizes and colors on your
  markup explicitly (for example `tbb:m-0` on a heading).
- **Own file per block**: `style.css` of each block scans only its own folder (`@source "./"`), so a block's CSS
  contains only the classes that block uses (about 3.6 KB for Sample Card).
- **Unlayered CSS on purpose**: the Tailbase theme styles headings without a cascade layer in the block editor.
  Unlayered class selectors win over those element selectors, so blocks look the same in the editor and on the
  front end.
- **Tokens**: `tokens.css` maps `tbb:bg-primary`, `tbb:bg-accent`, `tbb:bg-neutral` (and their `-contrast` / `-hover`
  variants) to the active theme's palette through `--wp--preset--color--*`, with fixed fallbacks for other themes.
  To change a color, edit the fallback or point the token at another preset.

Write classes as **complete strings** (`'tbb:bg-primary'`), never built from parts (`'tbb:bg-' + name`), or Tailwind
will not find them. Keep them in the block's `classes.js`.

## Where a class like `tbb:bg-primary` comes from

It is not written by hand. Tailwind generates it from a token:

1. **The token is declared** in `src/styles/tokens.css`:
   ```css
   @theme {
   	--color-primary: var(--wp--preset--color--purple-500, #383e61);
   }
   ```
   In Tailwind v4 every `--color-*` variable automatically becomes color utilities (`bg-primary`, `text-primary`,
   `border-primary`, ...). Only the name `primary` is ours.
2. **The prefix is added** by `prefix(tbb)` in `src/styles/tailwind.css`: the class becomes `tbb:bg-primary` and the
   variable becomes `--tbb-color-primary`.
3. **The class is generated only if it is found.** The block's `style.css` has `@source "./"`, so Tailwind scans that
   block's folder, finds the string `'tbb:bg-primary'` (in `classes.js`) and writes this into
   `build/<block>/style-index.css`:
   ```css
   .tbb\:bg-primary { background-color: var(--tbb-color-primary); }
   :root, :host { --tbb-color-primary: var(--wp--preset--color--purple-500, #383e61); }
   ```
4. **The color resolves in the browser.** `--wp--preset--color--purple-500` is generated by WordPress from the
   `purple-500` entry of the Tailbase theme's `theme.json` palette, so the block follows the theme. If that variable
   does not exist (another theme), the fallback `#383e61` is used.

To add a color, add a line to `tokens.css`, for example
`--color-danger: var(--wp--preset--color--orange-800, #663607);`, then rebuild. You can then write `tbb:bg-danger`,
as a complete string in the block's `classes.js`.

The theme's own `bg-purple-500` is a different class: it comes from the theme's Tailwind build, which this plugin does
not use.

## Add a new block

1. Copy `src/sample-card` to `src/<your-block>` and edit `block.json` (`name`, `title`, attributes).
2. Keep `style.css` as it is: it imports the shared setup and scans only the new folder.
3. Put controls in `src/<your-block>/controls/` and render them from `controls/index.js`.
4. Run `npm run build`. No PHP change is needed, because the plugin registers every `build/*/block.json`.

## Releasing

Commits follow Conventional Commits (`npm run commit`, enforced by commitlint). `npm run release` bumps the version in
`package.json` and `tailbase-blocks.php`, updates `CHANGELOG.md` and creates the GitHub release.
